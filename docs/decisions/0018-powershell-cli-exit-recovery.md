# ADR 0018 — восстановление оболочки после завершения CLI

Дата: 2026-10-31. Статус: принято для 0.4.0-preview.16.

## Контекст

На установленном OpenCode 2.0.32 выход из TUI воспроизводимо отключает console
handle родительской PowerShell 7. Она завершается через CLR FailFast с кодом
`0x80131623`; это подтверждено handle корневого процесса и собственным .NET
событием Win32 233. Восстановленный экран приглашения не доказывает, что процесс
жив. Ранее UI продолжал прямой ввод и показывал ошибку на последующие клавиши.

## Решение

Остановка PTY снимает прямой ввод и захват клавиатуры. Нативное поле возвращается
в командный режим; ошибку ввода в уже остановленный процесс заменяет статус.
Клавиша, совпавшая с остановкой, не переносится в новую оболочку.

`SessionManager` допускает одну попытку восстановления только при одновременно
выполненных условиях: точный код `0x80131623`, явно принятый запуск interactive CLI,
подтверждённое предыдущее приглашение, локальный `pwsh` со строго стандартными
аргументами и нашим `PS_PROMPT`. CLI-only, произвольные startup scripts и обычный
exit не подходят. Перед заменой весь вывод старого процесса должен быть прочитан.
Попытка потребляется до spawn; неудача не создаёт цикл повторов.

Создаётся новый PTY в той же вкладке. Журнал, блоки, черновик и архив ответов
переносятся; ожидающий ответ отменяется. Source/menu/composer состояния и очередь
ввода начинаются заново, epochs увеличиваются. Startup clear новой оболочки не
стирает сохранённый журнал; командный ввод ждёт подтверждённого приглашения.
Удаление старого PTY выполняется существующим ограниченным пулом завершения,
не блокируя UI. Пользователь получает явное сообщение о новом процессе.

## Ограничения и проверка

Локальные переменные не восстанавливаются. Достоверного источника текущего cwd
нет, поэтому используется каталог профиля. Последняя команда и прежние входные
байты не повторяются; private .NET handles и пользовательские настройки не меняются.

Нативные регрессии проверяют normal exit, два последовательных crash/recovery,
границы eligibility, сохранность данных и отсутствие retry при ошибке spawn.
Отдельно проверен настоящий изолированный OpenCode без запросов модели:
`/exit` → FailFast → новая оболочка в той же вкладке → успешная новая команда.

## Дополнение preview.23: закрытие канала раньше natural exit

WriteFile может вернуть Win32 232/233/109 до сигнала завершения pwsh. Прежний
fatal-path немедленно вызывал TerminateProcess с кодом 1, теряя точный CLR-код.
Writer также превращал WindowsError в строку, скрывая native код. Теперь Win32
HRESULT сохраняется как raw OS error через очередь; для других HRESULT
сохранён прежний формат ошибки.

Отдельный CliExitWatch принадлежит текущему PTY и создаётся только после
явно принятого interactive CLI в стандартной локальной PowerShell с известным
parent prompt. UI handoff и очистка остановленного ввода его не стирают.
После возврата совпадающего prompt действует окно 5 секунд; следующая принятая
обычная команда снимает watch. Повторный prompt не продлевает окно.

При native pipe-close квалифицированного процесса ввод сразу отключается,
но родитель не завершается принудительно: до 5 секунд от первой ошибки
продолжается неблокирующий drain/status poll. Повторные ошибки не продлевают
дедлайн; истечение проверяется даже без новой ошибки writer. Восстановление
по-прежнему требует exact 0x80131623 и полного drain. Normal exit, иной сбой,
CLI-only/custom startup/remote и отсутствующий ownership не создают restart.
При таймауте остаётся прежний fatal-path; отказ spawn не повторяется.

Регрессии используют настоящий закрытый ConPTY writer, задержанный родительский
exit, VT-query и опоздавшую пользовательскую клавишу до/после prompt handoff.
Проверяются независимый дедлайн, истёкший watch, новая обычная команда,
сохранение истории/черновика и отсутствие replay.

Финальный clear из старого источника не очищает журнал в Closing/Failed/Exited
или во время подтверждённого возврата CLI. Правило не зависит от сохранности
PendingChannelClose после получения exit-кода. Новая явно принятая shell-команда
снимает watch, поэтому обычный Clear-Host сохраняет своё действие.

## Дополнение preview.24: первая команда после возврата

Успех `PtyInputWriter::write` означает приём в очередь. Первая обычная команда
после CLI раньше немедленно снимала watch; следующий настоящий WriteFile мог
вернуть 232/109/233, и предусмотренное восстановление уже было недоступно.
Регрессия с ещё не писавшим writer закрытого ConPTY воспроизводит этот порядок:
enqueue успешен, фоновая запись завершается native ошибкой, родитель позже
доставляет natural CLR FailFast. До исправления сессия переходила в Failed.

Теперь обычная команда сохраняет исходное окно пяти секунд после возврата
CLI. Никакая следующая команда или повторный prompt его не продлевают.
Точный CLR-код и полный drain остаются обязательными; ошибка канала сама по
себе не разрешает restart. Обычная команда до подтверждённого возврата или
после истечения окна не сохраняет watch. Это ограниченное окно handoff,
а не утверждение, что enqueue подтвердил исполнение PowerShell.

Отдельный признак новой принятой shell-команды разрешает её явный Clear-Host
в Running, пока writer не сообщил ошибку. Его состояние проверяется до
обработки clear в первом финальном chunk, не только последующим state poll.
Подавление финального clear в Closing/Failed/Exited сохраняется.
Команды из очереди не переносятся в новую оболочку и не повторяются.
