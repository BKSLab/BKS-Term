# ADR 0007 — отдельный клиент Codex App Server

Дата: 26.10.2026. Статус: принято для ограниченного прототипа этапа 10.

## Основание

Концепция §8.5 предусматривает обычную вкладку Codex через ConPTY и отдельный
доступный клиент структурированного протокола. Экран TUI не даёт надёжной
структуры произвольного ответа или разрешения. App Server сообщает идентификаторы
диалога, запроса, действия и подтверждения непосредственно.

Проверены установленный **native Codex CLI 0.164.0**, его `--version`,
`app-server --help`, `app-server generate-json-schema --help` и схемы, полученные
локальной командой `app-server generate-json-schema --out <временная-папка>`.
Эти команды не запускают запрос к модели. Аутентификация и пользовательские
конфигурационные файлы при исследовании не читались агентом или BKS Term.

Основной источник протокола: [официальная документация OpenAI App Server](https://learn.chatgpt.com/docs/app-server).
Она описывает актуальный протокол; для реализации поля дополнительно сверены
со схемой установленной версии. Это существенно: например, в её обычном
command approval есть `kind` и `startedAtMs`, но нет описанного в текущей
документации `availableDecisions`.

## Решение

Три локальных модуля в `bks-app` изолированы от VT/ConPTY:

- `agent_protocol.rs`: проверка JSON-RPC, handshake, состояния диалога,
  поток текста и ревизии ожидающих подтверждений; без ввода/вывода.
- `agent_transport.rs`: отдельный worker, локальный stdio-процесс и
  ограниченные очереди; UI не выполняет pipe I/O и ожидание процесса.
- `agent_window.rs`: собственное нативное окно с EDIT/LISTBOX/BUTTON.

Открытие окна не запускает CLI. Только кнопка «Запустить App Server» разрешает
проверить `codex.exe --version` и выполнить `codex.exe app-server --listen stdio://`.
Внешний управляющий порт не открывается. Поддерживается только точный ответ
`codex-cli 0.164.0` от прямого абсолютного пути native executable; `.cmd` и `.ps1`
не используются. Проверка выполняется в worker с пределом 2 секунды/4 КиБ.

После `initialize` клиент ждёт успешный ответ, отправляет `initialized`, затем
`thread/start`. Указывается cwd, `sandbox: read-only`, `approvalPolicy: untrusted`,
`approvalsReviewer: user`, `ephemeral: true`. Ответ должен подтвердить схему,
режим readOnly без networkAccess, untrusted и reviewer user. При несовместимости
работа прекращается. Экспериментальные API не включаются. Сам протокол остаётся
экспериментальным upstream; gate не обещает поддержку будущей версии.

BKS Term не читает и не изменяет токены, не реализует login или refresh, не
передаёт свои ключи. При явном запуске App Server использует собственную обычную
конфигурацию и существующую авторизацию Codex. Для входа пользователь открывает
обычный Codex в терминале. Ошибка доступа остаётся ошибкой; автоповтора,
автовхода, переключения модели и автоматического перехода в PTY нет.

## Поддерживаемая поверхность

| Возможность | Поведение |
| --- | --- |
| Новый диалог | Один новый ephemeral thread на открытие/явный запуск окна |
| Ввод | Только текст до 16 КиБ; отправка отдельной кнопкой |
| Ответ | `item/agentMessage/delta`, конечный agentMessage без дублирования дельт, `turn/completed`, ошибки |
| Прерывание | Явный `turn/interrupt`; ранний запрос ждёт получения точного turnId |
| Обычный command approval | Полные параметры и JSON-RPC request ID, только accept/decline/cancel |
| Контекст | Transcript, текущий approval и состояние доступны в многострочных readonly EDIT с Tab-stop |
| Решение | Нативный список без начального выбора и отдельная кнопка передачи решения |
| Обычный режим | Явная кнопка «Открыть обычный терминал» возвращает вызывающему `Fallback(cwd)` с исходной папкой окна |

Нет resume/history, выбора модели, изображений, редактирования файлов,
произвольных tool/elicitation/form запросов, входа, постоянных правил,
`acceptForSession`, managed network и permissions approvals. Неподдерживаемый
server request отображается с контекстом и получает JSON-RPC `-32601`, без
утверждения действия. Слишком большой неподдерживаемый контекст может быть
усечён только в истории; его подтверждение всегда недоступно.

Прототип допускает только обычный `kind: command`, с command/cwd/itemId/turnId/
threadId/startedAtMs и известными полями. Нестандартный environment, network
context, предлагаемые постоянные amendments, новый вид действия и неизвестные
поля не сводятся к обычному «Разрешить». File change approvals отклоняются как
неподдерживаемые: интерфейс пока не собирает полный предложенный diff.

Read-only sandbox — исходная политика сервера. Явное разовое подтверждение
команды может разрешить действие за её пределами. Интерфейс показывает полные
параметры запроса, включая reason, cwd и идентификаторы; решение принимает человек.

## Актуальность и пределы

Каждый поддержанный pending approval хранит исходный ID с его JSON-типом,
threadId, turnId, itemId, полный отображённый контекст и возрастающую ревизию.
Проверка решения требует точного совпадения всех этих данных с первым ожидающим
запросом. Ответ `serverRequest/resolved`, завершение действия/turn, прерывание,
ошибка или закрытие инвалидируют соответствующий выбор. Повторный pending ID —
ошибка соединения. `cancel` также инвалидирует остальные решения этого turn.

Поток текста применяет минимальный `native_text::difference` через `EM_REPLACESEL`,
сохраняя native EDIT selection и первую видимую строку. Snapshot передаёт
`transcript_start`: накопленный объём удалённого текста в UTF-16 единицах native
EDIT после нормализации переводов строк, без служебного маркера. После отсечения
начала surviving selection и начало viewport ребазируются по этому счётчику;
viewport привязан к текстовой позиции через `EM_LINEINDEX`/`EM_LINEFROMCHAR`,
поэтому учитывается перенос длинных строк. Удалённая позиция ограничивается
началом оставшегося текста. Обычные дельты не сбрасывают место чтения.

Pending `turn/interrupt` связан с конкретным turnId. Завершение turn освобождает
его pending interrupt и сохраняет числовую границу уже выданных ID, без растущего
журнала. Поздние result/error завершённого interrupt не блокируют отмену нового
turn и не меняют его состояние.

Worker сначала разбирает уже поступившие уведомления, затем пользовательское
действие. Незавершённая строка тоже блокирует передачу решения. Строка с
повторными JSON-ключами на любой глубине считается неоднозначной и не принимается.
После выхода запроса на stdio актуальность на стороне сервера определяет сервер
по точному request ID; локальная ревизия не является удалённой транзакцией.

Ограничения: JSON-строка 128 КиБ, prompt 16 КиБ, история 192 КиБ UTF-8,
8 approvals по 24 КиБ контекста, 256 streamed item ID на turn, очередь UI
8 действий, очередь writer 16 ограниченных сообщений. Переполнение очереди
никогда не означает неявное подтверждение или повтор. Слишком длинная строка,
несовместимая схема, неоднозначность, переполнение approvals или непрерывный
backlog более 2 секунд останавливают соединение. Подключение ограничено 30 секундами.
Raw stderr дренируется без сохранения в историю или журнал приложения.

Каждый child создаётся с документированным `CREATE_SUSPENDED`, назначается
собственному неназванному Windows Job Object с `KILL_ON_JOB_CLOSE` и только затем
получает `ResumeThread`. Код child до назначения job не исполняется, потомки не
могут уйти из job в промежутке spawn/assign. Stable Rust 1.99 не предоставляет
стабильный доступ к primary-thread handle / spawn attributes, поэтому Toolhelp
находит единственный thread только свежесозданного собственного PID; его владелец
повторно проверяется через `GetProcessIdOfThread`. Неоднозначность или неожиданный
suspend count останавливают запуск. Недокументированные Nt-вызовы не используются.
API: [CREATE_SUSPENDED](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags),
[ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread).

Закрытие окна ставит atomic cancellation; worker закрывает job, дочерний процесс
и его потомков, освобождает pipes и writer. Это также снимает зависание writer,
если потомок держит унаследованный pipe. Существующие Codex-процессы не завершаются;
Toolhelp читает только метаданные thread list и не открывает чужие threads.
Job управляет жизненным циклом, а не заменяет sandbox самого Codex.

История окна хранится только в памяти BKS Term; после закрытия не восстанавливается.
У Codex остаётся его собственная политика конфигурации, журналов и обработки
данных. BKS Term не использует модель ради доступности терминала: введённый
пользователем prompt передаётся Codex только явной командой отправки.

## Проверка

Hermetic unit tests проверяют handshake/policy gate, поток текста, complete/error,
ранний interrupt, JSON и Unicode bounds, числовые/строковые IDs, устаревание,
duplicate keys/IDs, неизвестные и неоднозначные approvals, переполнение.
`tests/fixtures/codex-app-server.ps1` — локальный искусственный stdio peer,
запускаемый скрытым `powershell.exe -NoProfile -NonInteractive`: stream, interrupt,
oversize, silent, blocked stdin, early descendant и resolved approval. Он не запускает настоящий
Codex, не читает пользовательские файлы и не отправляет модельные/API-запросы.

Ручная приёмка остаётся отдельной: NVDA читает имена, transcript, полный approval
и выбранный вариант; Tab/Shift+Tab и Ctrl+A работают; Enter в prompt создаёт
новую строку, в истории/контексте/списке не подтверждает действие. Проверить
DPI 100/150/200%, High Contrast, отмену, закрытие при активном запросе и работу
обычной Codex-вкладки. Реальная авторизация, модельный ответ и настоящий approval
не считаются пройденными по fake-process тестам.
