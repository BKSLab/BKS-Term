# BKS Term — профили оболочек, вкладки и SSH

**Тип:** техническое задание для AI-агента-разработчика  
**Статус:** план следующей итерации  
**Платформа:** Windows 10/11 x64; Rust; существующий BKS Term  
**Приоритет:** высокая доступность с NVDA без регрессии текущего PowerShell-сценария

## 1. Контекст и цель

В BKS Term уже работает PowerShell, доступен ввод команд и просмотр результатов. Следующий этап — сделать **профили и несколько независимых терминальных вкладок** с привычной для Windows Terminal клавиатурной навигацией. Особый профиль — **SSH**, позволяющий быстро подключаться к сохранённым Linux-хостам.

Цель: в одном окне BKS Term держать PowerShell с Docker, WSL/Linux, Git Bash, Codex CLI и SSH-соединения, переключаясь между ними без потери выполнения, терминального состояния и фокуса NVDA.

### Важное ограничение существующей реализации

На текущем скриншоте приложение имеет **отдельное поле ввода команды и область вывода**. Для начального этапа это допустимо, но это ещё не полноценный интерактивный эмулятор. **AI CLI, `ssh`, `docker exec -it`, Bash, полноэкранные TUI, интерактивные prompts** требуют сквозного двустороннего потока ввода/вывода через ConPTY и терминального экрана, а не модели «выполнить строку → показать результат». Не маскировать эту разницу; на этапе интеграции устранить архитектурное ограничение. Временно разрешено сохранить старый режим как совместимый, явно назвав его «Командный режим».

## 2. Функциональный объём

### 2.1. Типы профилей

| Тип | Пример запуска | Требование |
|---|---|---|
| PowerShell 7 | `pwsh.exe` | Найти установленный исполняемый файл; не считать наличие обязательным |
| Windows PowerShell | `powershell.exe` | Поддержать Windows PowerShell 5.1 |
| CMD | `cmd.exe` | Стандартный профиль |
| Git Bash | установленный `bash.exe` (Git for Windows) | Проверить запуск с `--login -i` и совместимость с ConPTY |
| WSL | `wsl.exe -d <ИмяДистрибутива>` | Найти список дистрибутивов; создавать профиль для каждого |
| **SSH** | `ssh.exe <alias>` или `ssh.exe -p <port> -i <key> user@host` | Сохранённые удалённые подключения, работающие в собственной вкладке |
| Пользовательский | выбранный exe + массив аргументов | Ручная настройка |

Docker **не является отдельной оболочкой**, но должен работать из любого подходящего профиля. Допустимо добавить пользовательский профиль, запускающий конкретную Docker-команду, без внедрения в Docker API.

### 2.2. Менеджер профилей

- Автоматически обнаруживать доступные локальные оболочки: поиск исполняемых файлов, обнаружение WSL через `wsl.exe --list --quiet` (с обработкой кодировки/ошибок). Не запускать автоматически произвольные найденные программы для «проверки».
- Хранить стабильный `id`, отображаемое `name`, `kind`, `executable`, массив `args`, рабочий каталог, переменные окружения (без секретов), необязательные визуальные настройки.
- Позволять добавить, изменить, удалить пользовательский профиль; системные обнаруженные профили можно скрывать или переопределять без уничтожения источника обнаружения.
- Выбирать профиль по умолчанию. Отсутствующий бинарник не должен ломать приложение — показать доступную ошибку.
- Перед запуском проверять исполняемый файл и параметры; аргументы передавать **массивом**, избегая конкатенации командной строки и shell-инъекций.
- Не сохранять пароли, токены, passphrase и SSH-секреты в конфигурации и логах.

## 3. SSH-профили — обязательная часть задачи

SSH — **не отдельный собственный сетевой протокол в BKS Term** на первом этапе. Приложение запускает установленный системный **OpenSSH Client (`ssh.exe`)** в ConPTY и сохраняет полноценный интерактивный сеанс; проверка host key, запрос пароля/ключевой фразы, SSH-agent и конфигурация доверия остаются на стороне OpenSSH.

### 3.1. Возможности SSH-профиля

- Подключение по адресу или DNS-имени; логин и порт (22 по умолчанию); необязательный путь к приватному ключу.
- Отображаемое имя подключения, например `Prod API`, `Dev Ubuntu`.
- Поддержка SSH-алиасов из `%USERPROFILE%\.ssh\config` (полезно переиспользовать правила `Host`, `HostName`, `User`, `Port`, `IdentityFile`, `ProxyJump`). Предпочтительно запускать `ssh.exe <alias>`, чтобы OpenSSH сам разрешал конфигурацию.
- При ручном SSH-профиле безопасно формировать список аргументов: `-p`, `-i`, `-l`, имя хоста; никаких паролей в CLI или JSON.
- Для интерактивного сеанса использовать PTY на удалённой стороне в обычном порядке, при необходимости явно `-tt` как **настраиваемую** опцию, но не включать принудительно по умолчанию.
- Поддержать `ssh.exe -V` для проверки наличия клиента без обязательного подключения.
- После разрыва связи показывать состояние «Соединение завершено» и код выхода; не выполнять бесконечный автоматический реконнект. Команда «Переподключиться» создаёт **новую** сессию.
- Показать предостережение о первом подключении/изменении host key через обычный терминальный вывод, не обходить проверку ключей хоста; **не использовать `StrictHostKeyChecking=no`**.
- Отдельно тестировать: запрос подтверждения host key, пароль/ключевую фразу (без озвучивания введённых секретов), интерактивный `sudo`, `top` и другие TUI внутри SSH.
- Функции SSH должны работать независимо от наличия WSL или Git Bash.

### 3.2. Пример SSH-конфигурации OpenSSH

```sshconfig
Host dev-api
    HostName dev.example.org
    User deploy
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
```

Профиль BKS Term для этого хоста должен запускать `ssh.exe` с аргументом `dev-api`. `dev.example.org` здесь **пример**, не реальный сервер.

## 4. Вкладки и окна

### 4.1. Модель сессии

- Одна вкладка = одна независимая `TerminalSession`: `session_id`, `profile_id`, процесс/ConPTY, состояние ввода/вывода, экранный буфер и scrollback, заголовок, состояние выполнения, состояние доступного чтения.
- Переключение вкладок **не закрывает процесс** и не перезапускает окружение. Фоновая вкладка продолжает получать вывод; визуальное обновление можно оптимизировать, но данные не терять.
- Закрытие вкладки — закрытие конкретной сессии с корректным освобождением ресурсов. Если есть запущенный процесс, предлагать подтверждение в доступном диалоге; правила graceful shutdown и принудительного завершения документировать.
- Закрытие последней вкладки: на первом этапе оставить окно открытым и предложить новую вкладку; сделать поведение настраиваемым позднее.
- Новое окно запускает отдельную оболочку BKS Term и создаёт сессию выбранного профиля. Межпроцессный перенос вкладок **не входит в MVP**.
- Не реализовывать split panes на данном этапе; не путать вкладки с несколькими экземплярами приложения.

### 4.2. Windows-подобный интерфейс

В верхней части — горизонтальная полоса вкладок; каждая вкладка содержит название профиля или пользовательское имя, индикатор состояния, кнопку закрытия; справа — `+` (новая вкладка по умолчанию) и стрелка выбора профиля. Предусмотреть удобное масштабирование шрифта; выделенная вкладка различима не только цветом.

Контекстное меню вкладки: «Закрыть», «Переименовать», «Дублировать профиль в новой вкладке» (новая сессия, **не клонирование** процесса), «Открыть профиль в новом окне». Перетаскивание вкладок мышью — поздний этап, не приоритет.

### 4.3. Горячие клавиши (начальные значения, перенастраиваемые)

| Действие | Комбинация |
|---|---|
| Новая вкладка с обязательным выбором профиля, как по кнопке «+» | `Ctrl+Shift+T` |
| Выбор профиля новой вкладки | `Ctrl+Shift+P` (на первом этапе; впоследствии возможен конфликт с палитрой команд) |
| Следующая вкладка | `Ctrl+Tab` |
| Предыдущая вкладка | `Ctrl+Shift+Tab` |
| Перейти к вкладке 1…8 | `Alt+1` … `Alt+8`, после проверки конфликтов |
| Последняя вкладка | `Alt+9`, после проверки конфликтов |
| Закрыть вкладку | `Ctrl+Shift+W` |
| Новое окно | `Ctrl+Shift+N` |
| Список открытых вкладок | `Ctrl+Shift+L` (предложение, проверить конфликтность) |

**Принцип:** сочетания обрабатываются только в BKS Term; обычные вводимые символы, управляющие клавиши и не зарезервированные сочетания направляются в активную ConPTY-сессию. Сочетания должны быть изменяемыми, чтобы не конфликтовать с NVDA, PowerShell, Bash, nano, vim, Codex и другими TUI. Системные `Alt+Tab`, `Alt+F4` сохраняют стандартное поведение Windows.

## 5. Доступность и NVDA — критерий приёмки

1. Полоса вкладок представляется как доступный элемент типа Tab/TabItem либо эквивалентный поддерживаемый UIA-контрол. NVDA читает «Имя вкладки, номер из N, выбрана/не выбрана».
2. Меню выбора профиля — обычный доступный список/меню с фокусом, стрелками, Enter/Escape, без объектной навигации NVDA.
3. Кнопки «Новая вкладка», «Выбор профиля», «Закрыть вкладку» имеют понятные доступные имена, не озвучиваются только как `+`/`×`.
4. При переключении вкладки фокус возвращается в **соответствующий режим** выбранной сессии (интерактивный ввод или доступное чтение), а не в случайный элемент; восстановить положение чтения для каждой вкладки.
5. Создание вкладки озвучивает название профиля, но не повторяет весь накопленный буфер. Фоновый вывод не захватывает фокус.
6. Смена активной вкладки не прерывает чтение старой по причине перерисовки; новые сообщения не должны принудительно перемещать курсор чтения.
7. При завершении SSH-сессии — однократное понятное оповещение, без потока повторных live-region событий.
8. Диалоги закрытия, настройки профиля и ошибки запуска доступны через клавиатуру и UI Automation.
9. Отдельный механизм suppression для секретного ввода: **не озвучивать символы пароля/ключевой фразы через пользовательские события приложения и не сохранять их в истории**. Фактическое эхо ввода контролирует приложение и PTY; сценарий тестировать.
10. Отсутствие NVDA или её выключение не должно мешать обычной работе терминала.

## 6. Предлагаемая архитектура Rust

Не переписывать существующие проверенные модули без необходимости. Выделить следующие абстракции (имена ориентировочные):

```text
AppState
 ├── ProfileManager
 │    ├── ProfileDiscovery (PowerShell / CMD / Git Bash / WSL / OpenSSH)
 │    └── ProfileStore (версионированная JSON-конфигурация)
 ├── SessionManager
 │    ├── TerminalSession 01 ── ConPTY ── pwsh.exe
 │    ├── TerminalSession 02 ── ConPTY ── wsl.exe
 │    └── TerminalSession 03 ── ConPTY ── ssh.exe
 ├── TabManager / WindowManager
 └── AccessibilityCoordinator
      ├── UI Automation: вкладки и диалоги
      └── состояние доступного чтения для каждой сессии
```

Контракты:

- `Profile`: декларативная конфигурация запуска; не содержит процесс или живое соединение.
- `TerminalSession`: владеет ConPTY, запускаемым процессом, входным каналом, буфером и жизненным циклом; `session_id` не переиспользуется.
- `SessionManager`: `create(profile_id)`, `write(session_id, bytes)`, `resize(session_id, cols, rows)`, `close(session_id)`, события `Output`, `Exited`, `Failed`.
- `TabManager`: создаёт вкладку и связывает её с `session_id`; активная вкладка не определяет, работает ли процесс.
- `ProfileManager`: `discover`, `list`, `add`, `update`, `remove`, `set_default`, `validate`.
- `AccessibilityCoordinator`: подписывается на изменения активной сессии, не блокирует чтение ConPTY, обеспечивает независимую навигацию по вкладкам.

Использовать **ограниченные очереди**, потокобезопасный обмен сообщениями и backpressure для вывода; UI-поток не должен выполнять блокирующее чтение PTY, сетевые запросы или обработку длинных логов. Состояния `Starting`, `Running`, `Exited`, `Failed`, `Closing` должны быть явными. При больших потоках (`docker logs -f`) избегать накопления безлимитного буфера в памяти.

## 7. Конфигурация: пример схемы (без секретов)

```json
{
  "schema_version": 1,
  "default_profile_id": "powershell-7",
  "profiles": [
    {
      "id": "powershell-7",
      "kind": "local",
      "name": "PowerShell 7",
      "executable": "pwsh.exe",
      "args": [],
      "working_directory": null
    },
    {
      "id": "ubuntu",
      "kind": "wsl",
      "name": "Ubuntu (WSL)",
      "executable": "wsl.exe",
      "args": ["-d", "Ubuntu"],
      "working_directory": null
    },
    {
      "id": "dev-api",
      "kind": "ssh",
      "name": "SSH — Dev API",
      "executable": "ssh.exe",
      "args": ["dev-api"],
      "working_directory": null
    }
  ]
}
```

Путь к конфигурации: каталог данных приложения пользователя (`%APPDATA%\BKS Term\` или согласованный путь); для портативного режима — отдельная явная политика. Записывать атомарно, сохранять резервную копию перед миграцией, выводить читаемые сообщения об ошибках парсинга. `executable` не обязан находиться в PATH, разрешить абсолютный путь.

## 8. Порядок реализации для агента и контрольные точки

**Правило: одна небольшая функциональность → сборка `.exe` → ручная проверка с NVDA → фиксация дефектов → следующий шаг.** Не объединять всё в один большой PR. Не сообщать «готово», пока тест не проведён.

### Шаг 0. Аудит текущего BKS Term

- Проверить код и описать: как создаётся PowerShell, есть ли ConPTY, чем представлены ввод и экран, какие UIA-элементы доступны NVDA.
- Зафиксировать существующее рабочее поведение команды `docker ps` как регрессионный тест.
- Отдельно установить, где требуется переход от отдельного поля команд к полноценному интерактивному терминалу; не выдавать `stdin` одной команды за PTY.

**Приёмка:** краткий отчёт об архитектурных ограничениях и доступная сборка текущей версии.

### Шаг 1. Модель Profile + обнаружение

- `ProfileManager`, схема и валидация JSON; предустановленные PowerShell/CMD; Git Bash/WSL/SSH при наличии.
- Клавиатурно доступный диалог выбора профиля; выбор профиля по умолчанию.

**Проверить NVDA:** список профилей, названия, выбор Enter, Escape, ошибка отсутствующего исполняемого файла.

### Шаг 2. Независимые ConPTY-сессии

- `SessionManager`, две одновременно работающие сессии, отдельные ввод/вывод и scrollback.
- Реальный интерактивный `stdin/stdout` (включая обработку клавиш и resize); жизненный цикл процесса.

**Проверить:** запустить долгую команду в сессии A, другую команду в B; обе продолжаются, переключение не теряет вывод.

### Шаг 3. Вкладки и клавиатура

- Полоса вкладок, `+`, выпадающий список профилей, закрытие с подтверждением.
- `Ctrl+Tab`, `Ctrl+Shift+Tab`, `Ctrl+Shift+T`, настраиваемые остальные сочетания.
- Нативная семантика UIA и сохранение состояния чтения для каждой вкладки.

**Проверить NVDA:** 3 вкладки, переключение 30 раз, правильный фокус и объявление активной вкладки, никакого озвучивания фонового потока.

### Шаг 4. Git Bash и WSL

- Запуск установленных оболочек; корректная кодировка Unicode, изменение размера, пути/working directory.
- Переход `wsl.exe`, запуск команд Linux, завершение процесса.

**Проверить:** `pwd`, `ls`, `git status`, русский текст, `top` или аналогичная TUI; в среде без WSL показывать доступную ошибку, а не падать.

### Шаг 5. SSH-профили

- Создание и редактирование SSH-профиля; поддержка `~/.ssh/config` и алиасов без копирования приватных ключей.
- Проверки наличия `ssh.exe`, подключения, запроса host key и passphrase, разрыва соединения; кнопка переподключения.
- Поддержка нескольких одновременных SSH-вкладок.

**Проверить NVDA:** запрос доверия к host key, логин, безопасный ввод пароля/ключевой фразы, интерактивная Linux-оболочка, разрыв соединения и возврат к локальной вкладке.

### Шаг 6. Новые окна, UX и устойчивость

- Новое окно с выбранным профилем, сохранение default, восстановление **профилей**, но не автоматическое повторное подключение SSH/запуск команд без согласия.
- Внятное закрытие процессов, отсутствие утечек, проверка многократного создания/удаления вкладок.
- Настраиваемые хоткеи, минимальные нативные настройки интерфейса.

**Проверить:** десятки циклов создания/закрытия сессий; отсутствие зависших процессов, память не растёт без ограничения; NVDA работает после повторных переключений.

### Шаг 7. Регрессия AI CLI

- Запустить уже используемый CLI-инструмент в выделенной вкладке, проверить ввод, вывод и интерактивное подтверждение.
- **Не обещать полноценные доступные TUI-меню** на этом этапе: их семантическое распознавание — следующий отдельный проектный этап.

**Приёмка:** терминальные процессы работают корректно; дефекты чтения TUI выделены в отдельный backlog.

## 9. Обязательный чек-лист перед демонстрацией

- [ ] PowerShell запускается, `ls`, `git status`, `docker ps` отрабатывают.
- [ ] Создаются 3 вкладки с независимыми сессиями; процессы не завершаются при переключении.
- [ ] Есть список профилей, профиль по умолчанию, сохранение настроек после перезапуска.
- [ ] Git Bash и WSL доступны, **если установлены**; отсутствие обрабатывается корректно.
- [ ] Есть SSH-профиль с адресом/алиасом и портом/ключом через OpenSSH.
- [ ] SSH-вкладка поддерживает интерактивные запросы без отключения проверки host key.
- [ ] Ctrl+Tab / Ctrl+Shift+Tab работают как ожидается; все управляющие сочетания доступны для изменения.
- [ ] NVDA озвучивает названия вкладок и профилей и не переносит фокус из-за фонового вывода.
- [ ] Закрытие вкладки с работающим процессом требует подтверждения.
- [ ] Нет хранения паролей/секретов в JSON и диагностических логах.
- [ ] Собран релизный `.exe` командой `cargo build --release` и запущен вручную.

### Обязательный формат отчёта агента

1. Изменённые файлы и краткая суть.
2. Какие команды сборки/тестов выполнены и результаты.
3. Где находится собранный EXE.
4. Что проверено автоматически; что **должен** проверить пользователь с NVDA (агент не заявляет о проверке NVDA без реального тестирования).
5. Известные ограничения и следующий минимальный шаг.

## 11. Что не входит в эту итерацию

- Собственный SSH-клиент/шифрование вместо OpenSSH.
- Универсальное преобразование любых TUI-меню в UIA-элементы.
- Синхронизация профилей через облако, автоматическое хранение секретов.
- Разделение окна на панели, перетаскивание вкладок между окнами.
- Полноценная поддержка Linux/macOS как хост-платформ для BKS Term.
