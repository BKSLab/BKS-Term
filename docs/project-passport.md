# Паспорт проекта BKS Term

**BKS Term** — настольный терминал для Windows, в котором работа с программой экранного доступа NVDA и управление с клавиатуры заложены в основу продукта. Он предназначен для повседневной работы с командными оболочками, инструментами разработчика, удалёнными системами и интерактивными консольными приложениями.

| Параметр | Описание |
| --- | --- |
| Название | BKS Term |
| Бренд | BKS Lab |
| Тип продукта | Терминальный эмулятор с семантической доступностью |
| Целевая платформа | Windows 10/11 x64 |
| Основной язык | Rust |
| Технологическая основа | Нативный Win32-интерфейс, Windows ConPTY, VT/ANSI-модель, Windows UI Automation |
| Приоритет доступности | NVDA, полноценное управление без мыши |
| Лицензия | MIT |

## Зачем нужен проект

При работе в консоли незрячему пользователю недостаточно получить озвучивание текста. Нужно понимать, какая команда выполняется, где находится её результат, что изменилось на экране, какой пункт меню выбран и когда приложение ожидает ответа.

Интерактивные консольные приложения постоянно перерисовывают экран, перемещают курсор, показывают подсказки и выделяют элементы цветом. Терминальный поток обычно не сообщает, что перед пользователем именно меню, поле ввода или запрос подтверждения. Простое чтение изменяющихся строк создаёт речевой шум и затрудняет навигацию.

BKS Term создаётся как самостоятельная доступная рабочая среда, позволяющая выполнять терминальные задачи без запуска полноценной IDE только ради её встроенного терминала. Проект объединяет обычную терминальную совместимость, удобное чтение результатов и дополнительное понимание интерфейса поддерживаемых приложений.

## Цель проекта

Создать быстрый и устойчивый терминал, в котором пользователь NVDA может самостоятельно выполнять повседневные локальные и удалённые задачи, читать вывод и работать с интерактивными CLI через понятный клавиатурный интерфейс.

Для этого продукт должен обеспечивать:

- совместимость с привычными оболочками и консольными инструментами;
- доступное чтение экрана и истории с поиском, выделением, копированием и переходами между результатами;
- независимость чтения от поступающего вывода: новые данные не должны отбирать фокус или сбивать позицию пользователя;
- понятную обратную связь о вводе, ходе работы, завершении и запросах действия без непрерывного озвучивания перерисовок;
- удобную работу с распознанными полями, подсказками, меню и ответами TUI;
- несколько независимых сессий, настраиваемые профили запуска и быстрый доступ к рабочим окружениям;
- низкую задержку ввода, отзывчивый интерфейс и ограниченное потребление ресурсов при большом объёме вывода.

## Пользователи и основные сценарии

Основная аудитория — незрячие разработчики и технические специалисты, использующие NVDA. Управление с клавиатуры, история и навигация по результатам также полезны другим пользователям консоли.

| Сценарий | Что пользователь должен получать |
| --- | --- |
| Повседневная разработка | Запуск PowerShell, CMD и других установленных оболочек; работа с Git, Python, тестами, сборками и пакетными менеджерами. |
| Несколько рабочих окружений | Независимые вкладки и окна с отдельными процессами, папками, профилями и сохранённой позицией чтения. |
| SSH и удалённый Linux | Подключение стандартным OpenSSH-клиентом, выполнение команд и чтение удалённых TUI без установки компонентов BKS Term на сервер. |
| WSL и Docker | Запуск соответствующих внешних инструментов, интерактивная работа и чтение длительных потоков логов. |
| AI CLI | Ввод и редактирование запросов, чтение ответов, понимание хода выполнения и явное управление подтверждениями. Приоритетные инструменты — Codex, Claude Code, OpenCode, Kimi CLI и Gemini CLI. |
| Длительные задачи и меняющийся вывод | Чтение предыдущих результатов во время работы процесса, поиск нужного фрагмента и возврат к свежему выводу. |
| Работа без мыши | Управление вводом, чтением, вкладками, профилями, поиском, настройками и диалогами с клавиатуры. |

Это целевые сценарии продукта. Поддержка конкретного внешнего инструмента и удобство его интерфейса подтверждаются отдельными проверками.

## Основные принципы продукта

1. **Доступность как часть архитектуры.** Графическое отображение и доступное представление строятся из согласованного состояния терминала. Основной канал взаимодействия с программой экранного доступа — стандартные интерфейсы Windows, прежде всего UI Automation.
2. **Предсказуемое управление.** Ввод и чтение имеют понятные правила переключения. Пользователь может вернуться к вводу, не теряя контекст; фоновый вывод не захватывает управление.
3. **Достоверность представления.** Содержимое поля, выбранный пункт и готовность ответа определяются по подтверждённому состоянию приложения. При недостатке данных сохраняются полный доступный экран и обычный терминальный ввод.
4. **Управляемая озвучка.** Значимые события отделяются от анимации и повторных перерисовок. Пользователь выбирает степень автоматического озвучивания и может читать вывод вручную.
5. **Совместимость через общее ядро.** Специальные адаптеры дополняют стандартный терминал. Отказ дополнительного распознавания должен сохранять возможность ввода и чтения.
6. **Действия по выбору пользователя.** Текст TUI, ответа AI или распознанного меню сам по себе не является разрешением выполнить команду или подтвердить операцию. Перед отправкой действия проверяется актуальность исходного состояния.
7. **Локальная базовая доступность.** Для чтения терминала и распознавания поддерживаемых элементов не нужны облачная модель, обязательное сетевое подключение или специальный модуль NVDA. Использование сетевых AI CLI остаётся отдельным выбором пользователя.

## Архитектура и технологическая основа

Основа реализации — Rust и нативные API Windows. Приложение запускает существующие оболочки и CLI через ConPTY. Полученный терминальный поток преобразуется в модель экрана; эта модель служит источником для отображения, доступного чтения и анализа интерфейса.

| Компонент | Ответственность |
| --- | --- |
| `bks-pty` | Создание процессов и ConPTY-сессий, потоки ввода и вывода, размеры терминала и завершение процессов. |
| `bks-terminal` | Разбор VT/ANSI на базе `alacritty_terminal`, состояние экрана, история, курсор, стили и текстовые документы чтения. |
| `bks-app` | Win32-окна и элементы управления, вкладки, профили, настройки, отображение, доступность, навигация, уведомления и интеграции CLI. |

Ключевая архитектурная идея — **Semantic Accessibility Engine (SAE)**, семантический слой доступности. Он сопоставляет изменения терминала, выделяет значимые события, сохраняет извлечённый контекст и представляет достоверно распознанные элементы в удобной для чтения и управления форме. Соответствующая логика размещена в модулях приложения и адаптеров; терминальное ядро отделено от правил конкретных CLI.

Для доступного текста используются нативные элементы Windows, включая RichEdit, и их механизмы UI Automation. Адаптеры опираются на терминальные данные, координаты, стили и подтверждённые изменения. Там, где приложение предоставляет структурированный протокол, возможен отдельный доступный клиент к этому протоколу.

## Границы продукта и совместимость

BKS Term выполняет роль терминального эмулятора. Команды исполняют выбранная оболочка, дочерние программы и удалённые системы. SSH, WSL, Docker и AI CLI являются внешними инструментами и устанавливаются отдельно. Для удалённой работы используется их обычный терминальный поток.

Проект не предполагает безошибочного распознавания произвольного TUI. Терминал располагает только информацией, переданной приложением; версия, оформление и способ перерисовки могут влиять на распознавание. Базовый доступ к поддерживаемому экрану и истории дополняется распознаванием общих паттернов, адаптерами известных CLI и доступными структурированными протоколами.

Изменение внешнего CLI требует повторной проверки соответствующего адаптера. Наличие стратегии для инструмента не означает одинаковой полноты поддержки всех его экранов и версий. Архив распознанных ответов хранится в памяти вкладки и не является постоянной историей переписки между запусками.

Защищённый диалог ввода не меняет режим эха дочерней программы: его используют, когда программа уже ожидает скрытый ввод. Диагностика и сохранение данных должны учитывать конфиденциальность; автоматическая запись содержимого сессий на диск не входит в базовый сценарий. Запускаемые процессы работают с правами пользователя, терминал не изолирует их действия.

## Критерии качества и приёмки

Успешный результат проекта оценивается по повседневным пользовательским задачам:

- Пользователь NVDA может запускать оболочку, вводить и редактировать команды, читать и копировать результаты без запуска IDE.
- Основные действия доступны с клавиатуры; названия элементов, положение фокуса и возврат из чтения к вводу понятны и предсказуемы.
- Поиск, история и навигация позволяют находить нужный вывод; новые данные не нарушают самостоятельное чтение.
- Поддерживаемые интерактивные CLI корректно получают ввод, а распознанные поля, подсказки, запросы и ответы отражают состояние исходного приложения.
- Неоднозначность или отказ адаптера сохраняют обычный терминальный ввод и доступ к исходному экрану.
- Локальные, удалённые и контейнерные сценарии проходят проверку в соответствующих рабочих средах; их доступность не выводится из одних только локальных тестов.
- Длительный вывод, изменение размера, переключение вкладок и завершение процессов не приводят к потере управления или неконтролируемому росту памяти.
- Выпуск сопровождается запускаемым EXE, проверенными пакетами распространения, справкой и описанием существенных ограничений.

Автоматическая проверка включает форматирование, статический анализ, тесты, release-сборку, воспроизведение терминальных записей и проверки нативного интерфейса. **Фактическую речь, навигацию и удобство работы с NVDA подтверждает человек.** Автотесты и корректное UIA-дерево дополняют эту проверку.
