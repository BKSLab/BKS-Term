# BKS Term — подготовка окружения и итерационный план разработки

**Версия:** 0.2
**Дата:** 24 октября 2026 г.
**Статус:** рабочий план для разработчика и AI-агентов
**Связанные документы:** `docs/concept.md` (концепция продукта); `docs/BKS_Term_Профили_вкладки_SSH_ТЗ.md` (профили, сессии, вкладки и SSH); `docs/BKS_Term_Design_Spec_and_Reference/BKS_Term_Design/BKS_Term_UI_Design_Spec.md` (визуальный интерфейс и доступность редизайна). При противоречиях архитектурные изменения фиксировать отдельным решением.

## 1. Цель документа

Как можно раньше получить **реально запускаемый на Windows `.exe`**, проверять каждую небольшую итерацию вручную с **NVDA**, передавать агенту конкретную обратную связь и корректировать следующую итерацию. Не откладывать доступность до завершения графического интерфейса.

**Основные сценарии:** PowerShell/команды Git и Python; Docker и `docker compose`, включая `docker exec -it`; Codex CLI и другие интерактивные TUI; SSH на удалённые Linux-серверы; длинные логи; независимое чтение вывода через NVDA.

**Границы:** Windows 10/11 x64, нативный Rust/Win32, без Electron, обязательного расширения NVDA, облачных сервисов и искусственного «ИИ-распознавания» меню в MVP. Начальный прототип — один локальный сеанс; обновлённая дорожная карта последовательно добавляет профили, независимые вкладки, SSH и тёмный редизайн. Плагины и полноценная портативная поставка — позже.

## 2. Технологическое решение и важные оговорки

| Подсистема | Предлагаемое решение | Проверка / риск |
|---|---|---|
| Язык и сборка | Rust stable, Cargo, MSVC target | Проверить компиляцию на реальной Windows |
| Выполнение консольных процессов | Windows ConPTY через `windows` crate / подходящую обёртку | Корректно обрабатывать закрытие, resize и наследование handles |
| Терминальная модель | `alacritty_terminal` как кандидат, с закреплением версии | Провести spike: API, альтернативный экран, история, доступ к строкам и изменениям |
| Отрисовка и окно | **Нативный Win32 UI на Rust**; DirectWrite/Direct2D — кандидаты для текста | Не путать графический рендерер с интерфейсом доступности |
| Доступность | Windows UI Automation (UIA), собственные провайдеры при необходимости | Убедиться в чтении и управлении NVDA на реальном компьютере |
| Нативная область доступного чтения | Предпочитать системный текстовый контрол для раннего прототипа, позже решить архитектуру | Проверить чтение, выделение, поиск, фокус и скорость на больших объёмах |
| Семантический слой | Модуль Rust: поток событий, изменения экрана, классификация и адаптеры | Не считать экранный текст достоверной семантикой |
| AI CLI | Стандартный PTY-поток; специализированные адаптеры только как доп. режим | Проверять поддерживаемые версии/протоколы конкретных инструментов |
| Логи и диагностика | `tracing`, локальные файлы, обезличивание | Не сохранять секреты и полный вывод по умолчанию |

**Принцип:** технологические библиотеки — кандидаты до завершения технического исследования (spike). Не заставлять агента реализовывать сложный GPU-рендерер или UIA-провайдер до проверки простого рабочего пути. Никакая GUI-библиотека сама по себе не гарантирует доступность. Разделять терминальный эмулятор, рендерер, модель доступного текста и UIA.

## 3. Подготовка Windows: установка зависимостей

### 3.1. Предварительные проверки

Открыть **PowerShell**, выполнить команды по очереди:

```powershell
[System.Environment]::OSVersion.Version
$env:PROCESSOR_ARCHITECTURE
winget --version
git --version
rustc --version
cargo --version
```

Если команда не найдена — это не обязательно ошибка: инструмент пока не установлен. Убедиться, что целевая система поддерживает ConPTY (актуальные Windows 10/11). Для первой сборки использовать **x86_64-pc-windows-msvc**.

### 3.2. Git (если отсутствует)

```powershell
winget install --id Git.Git -e --source winget
```

Перезапустить PowerShell и проверить:

```powershell
git --version
```

### 3.3. Microsoft C++ Build Tools + Windows SDK

**Установить ДО Rust:**

1. Открыть https://visualstudio.microsoft.com/visual-cpp-build-tools/ (или Visual Studio Installer, если установлен).
2. Выбрать рабочую нагрузку **Desktop development with C++**.
3. Проверить присутствие **MSVC x64/x86 build tools** и **Windows SDK**.
4. Завершить установку. При запросе — перезагрузить компьютер.

Альтернатива для разработчика, который предпочитает командную строку: `winget install --id Microsoft.VisualStudio.2022.BuildTools -e` (если пакет доступен), затем в Visual Studio Installer добавить указанную нагрузку. **Простая установка пакета без C++ workload может оказаться недостаточной.** Не устанавливать полную Visual Studio IDE без необходимости.

**Примечание о лицензиях:** условия использования Microsoft Build Tools зависят от редакции и сценария; для личного/open-source проекта обычно подходят разрешённые бесплатные варианты, но проверить действующую лицензию.

### 3.4. Rustup / Rust / Cargo

Официальный сайт: https://rustup.rs/ . Возможная установка из PowerShell:

```powershell
winget install --id Rustlang.Rustup -e --source winget
```

Запустить новое окно PowerShell; при первом запуске rustup выбрать **stable MSVC** (не GNU). Проверить:

```powershell
rustup show
rustc --version
cargo --version
rustup target list --installed
```

При необходимости задать целевую платформу явно:

```powershell
rustup default stable-x86_64-pc-windows-msvc
rustup component add clippy rustfmt
```

Если `cargo` не находится, перезапустить терминал и проверить `%USERPROFILE%\.cargo\bin` в `PATH` (для PowerShell: `$env:USERPROFILE\.cargo\bin` — только описание пути, не команда).

### 3.5. NVDA и необязательные инструменты

- Проверить актуальную версию NVDA и запомнить настройки речи/озвучивания; для тестов лучше сохранять стабильный профиль.
- Для разработки необязателен VS Code: всё собирается через Cargo. Но VS Code + rust-analyzer могут помочь агенту и разработчику.
- Не устанавливать Docker ради сборки терминала. **Docker Desktop**, OpenSSH и Codex CLI нужны только для соответствующих пользовательских тестов, если они ещё не установлены.
- Не требуется Python, Node.js, Electron или специальный плагин NVDA для базового приложения.

### 3.6. Smoke test среды

```powershell
mkdir BKS-Term-Workspace
cd BKS-Term-Workspace
cargo new rust-smoke
cd rust-smoke
cargo run
cargo build --release
.\target\release\rust-smoke.exe
```

**Условие завершения:** сообщение `Hello, world!` появляется; release `.exe` запускается без Rust IDE. Если `link.exe not found` / `kernel32.lib not found`, сначала исправить MSVC и Windows SDK, не менять архитектуру проекта.

## 4. Организация репозитория и контур работы с агентами

Рекомендуемое дерево (можно уточнить после spike):

```text
bks-term/
  Cargo.toml                  # Rust workspace
  Cargo.lock                  # коммитить для приложения
  README.md
  docs/
    concept.md
    setup-and-iterations.md
    decisions/                # ADR: архитектурные решения
    testing/
      nvda-checklist.md
      feedback-log.md
  crates/
    bks-app/                  # точка входа и окно
    bks-pty/                  # ConPTY, жизненный цикл процессов
    bks-terminal/             # VT parser / terminal model
    bks-accessibility/        # UIA, доступный текст, события
    bks-semantic/             # распознавание изменений и TUI
  tests/
    fixtures/                 # обезличенные записи потоков TUI
  scripts/
    package.ps1
```

**Правила для AI-агента:**

1. На одну итерацию — **одна проверяемая возможность**; не перерабатывать соседние подсистемы без согласованного ADR.
2. Сначала дать короткий план файлов/изменений, затем код, затем фактические результаты проверок.
3. После этапа выполнять `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo build --release` (если этап допускает). Не писать «проверено», если не запускалось.
4. Выдавать точный путь к `.exe`, git commit, список изменений и известные ограничения.
5. Не объявлять NVDA-тест успешным по одному прохождению автоматических тестов: нужен человек, работающий с NVDA.
6. Не повышать сложность до доступных меню, пока вывод в отдельном буфере не читается надёжно.
7. Отсутствие прямого API у библиотеки = повод для spike и ADR, а не для обхода через недокументированные внутренности.
8. Никакие CLI-команды, полученные из распознанного текста, не исполнять автоматически.

## 5. Итерационная дорожная карта: собрали → запустили → проверили → исправили

Сроки ниже **ориентиры, не обязательства**: зависят от доступных API и ручного тестирования NVDA. Каждая итерация должна завершаться запускаемым артефактом, кроме исследований без кода.

### Этап 0. Подготовка среды (0,5–1 день)

**Задачи:** установить Git, MSVC + SDK, Rust; выполнить smoke test; создать репозиторий и первичный README.

**Приёмка пользователем:** `cargo run`, `cargo build --release` работают; доступен исполняемый файл.

**Обратная связь:** прислать точный текст ошибок установки/сборки и версии инструментов.

### Этап 1. Окно BKS Term и минимальный ConPTY (2–5 рабочих дней)

**Задачи:** создать нативное окно с заголовком BKS Term; запустить PowerShell как дочерний процесс через ConPTY; передавать ввод и показывать текстовый вывод в простом контроле. Корректно закрывать процесс и handles.

**Важно:** это может быть пока **не полноценный терминальный эмулятор**: задачи `clear`, перемещения курсора и TUI ещё не обязаны работать. Простой текстовый контрол годится как инженерный spike.

**Проверить:** ввод `echo test`, `pwd`, `git --version`; окно закрывается без зависания; NVDA определяет окно и доступный текст.

**Стоп-критерий:** если NVDA вообще не может читать текст, не начинать реализацию вкладок/рендера.

### Этап 2. Полный редизайн и визуальная основа по референсу

Сначала выполнить Итерацию 0 из спецификации редизайна: зафиксировать архитектуру, скриншот «до», рабочий коммит и ограничения командного режима. Затем сделать визуальную основу **до профилей, вкладок и VT-модели**, чтобы новая функциональность подключалась к готовым компонентам без повторного редизайна.

**Задачи:** централизовать тёмные дизайн-токены, типографику, отступы, DPI и состояния hover/focus; создать новую компоновку окна, строку состояния и стили вкладок, боковой панели, кнопок, меню и терминальной поверхности. Текущие вывод и поле команды оформить по референсу, убрать тяжёлые рамки, реализовать подсветку текущей строки без потери доступности. Сохранить навигацию по блокам, копирование, иконку и все действующие сочетания.

**Ограничение:** не показывать фиктивные вкладки, SSH, пункты панели, кнопки или статусы. Компоненты и их визуальные состояния можно подготовить заранее, но отображать только с реальными действиями и достоверными данными.

**Промежуточная обратная связь 24.10:** текущая оболочка с реальными sidebar и одной PowerShell-вкладкой принята пользователем условно, но полного соответствия референсу нет, прежде всего по цветам. Базовый почти чёрный фон и белый основной текст уже используются; полноценной цветовой обработки вывода ещё нет. Не считать цветовую доводку завершённой: уточнить палитру в финальных визуальных итерациях, а ANSI/SGR/256/True Color реализовать отдельно на Этапе 5, без имитации раскраски по словам.

**Проверить:** визуальное соответствие референсу в рамках текущей функциональности; прежние PowerShell-сценарии и горячие клавиши, фокус, Tab-навигацию, NVDA, маленькое окно и масштабирование 100/150/200%. Редизайн разбить на небольшие сборки и останавливаться после каждой для обратной связи пользователя.

### Этап 3. Профили и независимые сессии с прямым PTY-вводом

**Задачи:** реализовать `Profile`, `ProfileManager`, версионированное хранилище без секретов и обнаружение PowerShell/CMD, а также Git Bash/WSL/OpenSSH при наличии. Затем выделить `SessionManager`: одна сессия владеет своими ConPTY, вводом, выводом, буфером и жизненным циклом. Реализовать прямой интерактивный ввод, управляющие клавиши и resize; старый «Командный режим» сохранять до проверенной замены.

**Проверить:** две одновременные сессии продолжают работать независимо; длительная команда в A не мешает B; отсутствующий исполняемый файл даёт доступную ошибку; аргументы передаются массивом. Проверить сохранение профилей и выбор профиля по умолчанию с клавиатуры и NVDA.

### Этап 4. Настоящие вкладки и боковая навигация

**Задачи:** связать полосу вкладок с `SessionManager`; добавить создание, закрытие с подтверждением, выбор профиля, `Ctrl+Tab`/`Ctrl+Shift+Tab` и доступные UIA-роли. Подключить реальные действия к уже оформленным на Этапе 2 компонентам вкладок и компактной боковой панели, не повторяя редизайн. Для каждой сессии хранить режим фокуса, позицию чтения, историю команд и незавершённый черновик.

**Проверить:** минимум три вкладки, многократные переключения без остановки процессов и потери вывода; фоновый вывод не захватывает фокус; NVDA объявляет имя, положение и выбранное состояние вкладки. Up/Down в многострочном редакторе сначала двигают caret, история открывается на первой/последней строке.

### Этап 5. Полноценная терминальная модель, поверхность и ANSI

**Задачи:** интегрировать VT-движок-кандидат (`alacritty_terminal` или обоснованную замену); обрабатывать escape-последовательности, Unicode, курсор, resize, прокрутку и alternate screen; отделить модель от рендера. Вывести VT-ячейки на уже оформленную цельную терминальную поверхность, сохранив реализованную ранее подсветку строки. Отдельное поле команды удалять только после регрессионной проверки прямого ввода.

**Цвета:** поддерживать SGR, foreground/background, 16/256 цветов и True Color по палитре из спецификации редизайна; не раскрашивать вывод по словам и не делать весь терминал зелёным.

**Проверить:** `cls`, цветной вывод, `git log`, большие объёмы текста, PowerShell prompt и интерактивный CLI. Сравнить с Windows Terminal: без ANSI-мусора, дублирования и потери ввода.

### Этап 6. Доступный буфер NVDA — ключевой этап MVP

**Задачи:** предоставить полный доступный снимок/историю для каждой сессии; переключение между интерактивным вводом и чтением; копирование, поиск, сохранение позиции чтения при новом выводе. Синхронизировать доступное представление с VT-моделью, не связывая его с визуальным курсором TUI.

**Проверить с NVDA:** чтение построчно и посимвольно, выделение, копирование, возврат к вводу, стабильный фокус при логах и переключении вкладок.

**Критерий MVP-A:** обычные команды, чтение вывода и переключение режимов удобны для ежедневного использования. При неудовлетворительном результате возвращаться к этапу 6, а не переходить к AI CLI.

### Этап 7. Git Bash, WSL, SSH, Docker и долгоживущие процессы

**Задачи:** проверить Git Bash и WSL, если установлены; реализовать создание и редактирование SSH-профилей через системный `ssh.exe`, включая алиасы OpenSSH, порт и ключ без копирования секретов. Поддержать несколько независимых SSH-вкладок, состояние завершения и явное переподключение новой сессией. Ограничить scrollback и очереди, настроить backpressure.

**Проверить:** `pwd`, `ls`, `git status`, русский текст, `docker ps`, `docker exec -it`, `docker compose logs -f`; локальный PowerShell → SSH → Linux shell; host key, пароль/passphrase без озвучивания и сохранения, `sudo`, TUI, Ctrl+C, разрыв соединения. Не использовать `StrictHostKeyChecking=no`; отсутствующие среды и недоступные ручные сценарии явно отмечать **не проверено**.

### Этап 8. Управление уведомлениями и шумом TUI

**Задачи:** различать новый вывод и повторную перерисовку; не отправлять каждую анимацию как речевое событие; ввести режимы автоматического объявления (всё новое / только важное / без автосообщений); ограничивать события по частоте. Чтение по требованию остаётся полным; завершение SSH объявляется однократно.

**Проверить:** прогресс-индикатор, логи, повторное обновление одной строки, фоновые вкладки, ошибка в потоке; тест с NVDA на реальном CLI.

### Этап 9. Первый доступный TUI-диалог (1–3 недели)

**Задачи:** выбрать **один конкретный CLI и конкретную версию** (например, используемую пользователем версию Codex); зафиксировать образцы экранов; реализовать консервативное распознавание диалога подтверждения; предоставить стандартные UIA-элементы выбора; преобразовывать явный выбор пользователя в подтверждённые клавиши CLI.

**Безопасность и корректность:** при изменении состояния исходного TUI инвалидировать распознанное меню; по недостаточной уверенности — обычный режим, не угаданный выбор. Никогда не отправлять Enter и не подтверждать запуск команды автоматически. Особые запросы на разрешения и потенциально разрушительные команды не упрощать до автоматического «Да».

**Проверить:** все пункты озвучиваются; NVDA сообщает выбор; пользователь может отменить; после изменения меню нельзя активировать устаревший пункт.

### Этап 10. Интеграционные адаптеры AI CLI (исследование + итерации)

**Задачи:** для поддерживаемых программ оценить документированные структурированные протоколы, поток событий и версионирование; предусмотреть отдельный адаптер. Основной запуск через ConPTY **сохраняется всегда**. Адаптер — дополнительный способ построения семантических представлений, не обязательный для всех CLI.

**Проверить:** если структурированный API недоступен, программа остаётся работоспособной как обычный терминал; конфиденциальные данные не отправляются в сторонние сервисы. Проверить регрессию уже используемого AI CLI в отдельной вкладке.

### Этап 11. Новые окна, UX и устойчивость

**Задачи:** новое окно с выбранным профилем; настраиваемые горячие клавиши; поведение закрытия последней вкладки; восстановление профилей без автоматического запуска команд и SSH; десятки циклов создания/закрытия сессий. Довести DPI, High Contrast, Reduced Motion, длинные имена, переполнение вкладок и компактную боковую панель.

**Проверить:** отсутствие зависших процессов и утечек, ограниченная память при логах, стабильная NVDA после переключений, читаемость и клавиатурное управление при 100/150/200%.

### Этап 12. Упаковка, обновления и релизная дисциплина (после MVP)

**Задачи:** portable `.zip`, установщик, чистая установка и удаление, CI-артефакты, контроль DLL/VC Runtime зависимостей, журнал изменений, политика версий; цифровая подпись по возможности.

**Проверить:** запуск на **втором чистом ПК или VM**, где нет Rust и Build Tools. Не считать `cargo build --release` готовым пользовательским инсталлятором.

## 8. Короткий чек-лист NVDA для каждой сборки

- [ ] Окно BKS Term определяется и доступно с клавиатуры.
- [ ] После запуска очевидно, где фокус и как перейти к вводу.
- [ ] Ввод команды работает, Enter отправляет её только при намеренном нажатии.
- [ ] Можно прочесть новый вывод и вернуться к старому, не используя объектную навигацию NVDA.
- [ ] Чтение текста построчно/посимвольно и копирование не ломаются.
- [ ] Новые строки не выбивают из режима чтения.
- [ ] Ctrl+C и другие команды доходят до приложения, когда фокус в терминале.
- [ ] При долгом выводе окно не подвисает; NVDA не захлёбывается обновлениями.
- [ ] В TUI выбранный пункт читается только если его корректно удалось распознать.
- [ ] При ошибке подключения или завершении процесса появляется понятное сообщение.
- [ ] Не происходит непреднамеренного подтверждения команд/разрешений.

Фиксировать результат каждого пункта: **пройдено / не пройдено / не реализовано / не проверено**. Не смешивать эти статусы.

## 9. Нефункциональные критерии и измерения

Начальные ориентиры для оценки, а не неподтверждённые гарантии:

- **Запуск:** фиксировать время до активного поля ввода на тестовом компьютере.
- **Память:** фиксировать потребление на пустом окне, после 10 000 строк и через 30 минут логов.
- **Ввод:** не допускать заметных задержек набора команд.
- **Вывод:** не блокировать основной UI-поток обработкой больших объёмов ANSI-данных.
- **NVDA:** фиксировать лишние речевые объявления, потерю фокуса и возможность прочесть завершённые сообщения.
- **Надёжность:** освобождение ConPTY handles, корректное завершение дочернего процесса, отсутствие потери последних строк при закрытии.
- **Приватность:** логирование stdout/stderr и содержимого удалённых сессий **выключено по умолчанию**, дампы для отладки — только по осознанному включению и с очисткой секретов.

После первых замеров утвердить **конкретные числовые пороги** в ADR/тест-плане. Не обещать низкое потребление памяти или безупречную производительность только потому, что используется Rust.

## 10. Что запрещено считать решённым раньше времени

1. «Текст появился в окне» ≠ полноценный ANSI/VT терминал.
2. «NVDA озвучила заголовок окна» ≠ доступный буфер терминала.
3. «На экране видно меню» ≠ терминал знает его пункты и выбранное состояние.
4. «Поддерживает SSH» ≠ все удалённые TUI автоматически доступны.
5. «Собрали EXE» ≠ приложение будет работать на любой Windows без проверки зависимостей.
6. «Есть UIA» ≠ интерфейс удобен: обязательно тестировать клавиатуру, фокус и речевые события.
7. «Используем Rust» ≠ отсутствие зависаний: нужны метрики и регрессионные проверки.
