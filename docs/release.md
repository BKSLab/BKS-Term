# Сборка и выпуск BKS Term

## Версия и условия выпуска

Единственный источник версии приложения — `crates/bks-app/Cargo.toml`.
Номер пакета, внутренний `package-manifest.json`, внешний manifest и имя
архива используют эту версию, включая суффикс, например `0.2.0-preview.1`.
Упаковщик требует её совпадения с ресурсом ProductVersion самого EXE,
чтобы не передать старую сборку под новым номером.
Библиотечные crate могут иметь собственные версии.

Используется SemVer: patch — исправления совместимого поведения, minor —
новые возможности, major — несовместимость. До 1.0 заметные изменения
сочетаний клавиш, формата профилей или озвучивания требуют minor и описания
миграции в CHANGELOG. Непроверенная человеком сборка остаётся prerelease.
Смена одной только подписи или переупаковка не оправдывает новое поведение;
контрольные суммы пересчитываются при каждом изменении артефактов.

## Требования и сборка

Для пользователя: Windows 10/11 x64 с ConPTY, Windows PowerShell 5.1 и
стандартным для этой системы .NET Framework 4.x (для установщика).
Оболочки PowerShell, CMD, OpenSSH и другие внешние CLI поставляются отдельно.
Rust и Build Tools на пользовательской машине не нужны. Это требование
нужно подтвердить запуском на чистой VM, а не только анализом DLL.

Для сборки нужны Rust stable MSVC, Visual Studio Build Tools и Windows SDK
с `rc.exe`, `dumpbin.exe` и встроенный компилятор .NET Framework `csc.exe`.
Release использует статический CRT. Упаковщик отклоняет прямые импорты
VCRUNTIME/MSVCP/CONCRT и отладочного UCRT; системный UCRT Windows допускается.
`dependencies.txt` содержит фактический вывод `dumpbin /dependents`, а не
обещание отсутствия любых динамических зависимостей во внешних оболочках.

Из корня репозитория:

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --release
.\packaging\test-package.ps1
.\scripts\package.ps1 -Exe .\target\release\bks-app.exe -OutputDirectory .\target\packages
$portable = Get-ChildItem .\target\packages -Filter '*-portable.zip' | Select-Object -First 1
.\packaging\test-package.ps1 -PortableArchive $portable.FullName
```

`-Version` необязателен и обязан совпадать с Cargo; `-Dumpbin` позволяет
явно выбрать инструмент; `-Csc` задаёт компилятор bootstrap установщика.
Упаковщик не компилирует приложение и не запускает
его. Проверяйте, что передан именно результат выполненной release-сборки.

## Содержимое пакетов

В `target/packages` создаются portable ZIP, настоящий self-extracting
`*-setup.exe`, отчёт о DLL, внешний manifest и SHA256SUMS. В ZIP находятся
`bks-app.exe`, установочные скрипты, лицензия MIT, CHANGELOG, README,
справка `docs/help.md`, список `docs/known-limitations.md`, эта инструкция и
руководства ручной проверки.
Внутренний manifest содержит SHA256 и размер каждого файла, кроме самого
manifest; внешний SHA256SUMS покрывает архив, EXE, отчёт и внешний manifest.

Небольшой .NET Framework bootstrap встраивает архив и PowerShell-установщик
в EXE; manifest `asInvoker` задаёт запуск без повышения прав. При сборке проверяются
извлечение EXE в отдельный каталог и точное совпадение вложенных файлов.
Эта проверка использует `--extract-only` и не устанавливает приложение. Проверки скриптов
работают в частных каталогах, с отдельным APPDATA, без пользовательского
реестра и меню «Пуск». Чистая VM и NVDA остаются ручными проверками.

Сборки сейчас **без цифровой подписи** (`unsigned` в manifest).
При появлении сертификата подписываются сначала `bks-app.exe`, затем
установщик; после подписи пакеты и SHA256 пересоздаются. Сертификаты и
закрытые ключи в репозиторий не добавляются. Перед распространением должны
быть проверены статус подписи и актуальные суммы окончательных файлов.

## Установка, обновление и удаление

Portable: распакуйте ZIP в отдельный каталог и запустите `bks-app.exe`.
Настройки и профили, в том числе у portable-версии, находятся в
`%APPDATA%\BKS Term`; portable здесь означает отсутствие обязательной
установки, а не хранение настроек рядом с EXE.

Для установки запустите `*-setup.exe` обычным пользователем. Приложение
копируется в `%LOCALAPPDATA%\Programs\BKS Term`, появляется ярлык в меню
«Пуск» текущего пользователя и запись удаления только в HKCU. Приложение
после установки автоматически не запускается. Интеграция контекстного меню
Проводника выполняется отдельно явной командой пользователя.

Тот же результат из распакованного ZIP:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install.ps1
```

Чтобы обновить сборку, закройте BKS Term и запустите новый установщик.
Файлы проверяются по SHA256. Чужой непустой каталог и изменённый управляемый
файл не перезаписываются. Неизвестные файлы внутри установленного каталога
сохраняются; устаревшие управляемые файлы удаляются только при совпадении
их прежнего SHA256. При неудаче копирования закройте работающий терминал
и повторите тот же установщик. Профили и настройки не мигрируют молча.

Перед удалением закройте BKS Term; заблокированные файлы останавливают
удаление до изменения установки. Удаление доступно в параметрах приложений Windows или командой:

```powershell
& "$env:LOCALAPPDATA\Programs\BKS Term\uninstall.ps1"
```

Удаляются только неизменённые файлы собственного install-manifest, собственный
ярлык и собственная запись HKCU. Если пользователь включал меню Проводника,
его два пункта удаляются только при точном совпадении пути владельца и команды
с установленным EXE; чужие и изменённые пункты сохраняются.
Изменённые и неизвестные файлы сохраняются.
Профили и настройки сохраняются по умолчанию. Их явное удаление:

```powershell
& "$env:LOCALAPPDATA\Programs\BKS Term\uninstall.ps1" -RemoveData
```

`-RemoveData` удаляет только `profiles.json`, `settings.json` и `workspace.json` в текущем
APPDATA и их три известных незаблокированных файла `*.json.lock`;
занятые lock-файлы и неизвестные файлы сохраняются. Перед удалением данных
закройте все окна BKS Term. Каталоги с junction/symlink
отклоняются. Для особого каталога используйте `-InstallDirectory` как при
установке, так и удалении. `-SkipIntegration` предназначен для изолированных
проверок: он не создаёт и не удаляет пользовательские ярлыки/ключи.

## Ручная приёмка перед релизом

На чистой Windows x64 без Rust/Build Tools, с обычной учётной записью:

1. Проверить SHA256 скачанных ZIP/EXE и статус подписи.
2. Распаковать ZIP в путь с пробелами, запустить EXE, выполнить простую
   команду, открыть F1. Зафиксировать версию Windows и доступные оболочки.
3. Запустить установщик без повышения прав, проверить расположение, ярлык
   и удаление в параметрах приложений. Проверить отсутствие запросов DLL.
4. Создать профиль и изменить режим озвучивания. Закрыть терминал,
   повторно установить/обновить и проверить сохранность настроек.
5. Добавить свой файл в каталог приложения. Удалить приложение: чужой файл
   и APPDATA должны остаться; ярлык и запись удаления — исчезнуть.
6. Повторить установку и отдельно проверить явное удаление данных.
7. С NVDA пройти сценарии из `manual-*.md`, фиксируя каждый пункт как
   «пройдено», «не пройдено», «не реализовано» или «не проверено».

В релизном отчёте указываются точные версия, SHA256 EXE, Windows/NVDA,
результаты автоматических команд и оставшиеся ручные пункты.

## CI

`.github/workflows/windows.yml` выполняет fmt, clippy, тесты, release,
fixture-проверки установки/удаления и упаковку на Windows. ZIP, EXE,
manifest и суммы сохраняются как build artifacts на 30 дней. Workflow
не публикует GitHub Release и не меняет пользовательские настройки.
Локальное наличие workflow не означает, что он уже выполнен в GitHub.
